## Context

로스터는 하루 5-20 배치를 처리한다. 현재 앱은 배치 하나만 지원하며 계획/추적 기능이 없다. 사용자는 화이트보드/종이에 계획을 적거나 기억에 의존한다.

## Vision

### 10x Check
단순 체크리스트가 아니라 **로스팅 운영 OS**. 아침에 앱을 열면 오늘 8배치, 예상 4시간 30분이 보인다. 배치마다 원두 원산지, 투입량, 프로파일, 예상 드롭 시간이 표시된다. "시작" 누르면 ActiveRoast가 모든 메타데이터로 미리 세팅된 채 열린다. 로스트 완료 → 자동으로 plan 뷰로 복귀, 실제 수율(투입 500g → 배출 430g) 인라인 표시. 하루 끝: "8배치, 그린 4.2kg → 로스트 3.4kg, 평균 DTR 11.2%" 원클릭 요약.

### Platonic Ideal
로스터가 기억을 쥐어짜지 않아도 된다. 앱이 "다음에 뭘 해야 하는지" 알려준다. 순서 변경은 드래그, 긴급 추가는 2탭, 완료는 자동. 퇴근 시 오늘 계획이 그대로 History에 쌓인다.

## Accepted Scope (이번 구현 포함)

- **Plan 뷰 신설** (`src/views/Plan.tsx`) — 오늘의 로스팅 배치 큐
  - 배치 추가 (원두명, 투입량g, 프로파일 선택 optional)
  - 배치 편집/삭제
  - 상태: `pending` | `in-progress` | `done` | `skipped`
  - 날짜별 저장: `tauri-plugin-store` 사용 (`LazyStore('plans.json')`, 이미 프로젝트에 설치됨)
- **E1: Seamless Handoff**
  - Plan 뷰의 "다음 로스트 시작" → ActiveRoast에 `PlanBatchContext` 전달
  - ActiveRoast 완료 시 plan 뷰로 복귀, 해당 배치 자동 done 마킹
- **E2: ETA 헤더**
  - 남은 배치 × 예상 시간 합산 → `"남은 예상 시간: 약 Xh Ymin"`
  - 현재 Profiles mock data에 `totalTimeSec` 없음 → V1은 600초(10분) fallback만 사용
  - ETA 헤더 표시: `"남은 예상: 약 Xh Ymin (Profiles 데이터 미입력, 배치당 10분 기준)"`
  - Profiles가 실데이터화될 때 `estimatedTimeSec?: number` 필드 추가 예정 (TODOS)
- **E3: Inline Results**
  - 완료 배치 카드에 실제 투입량, 배출량(사용자 입력), 총 로스팅 시간, DTR 표시
  - 배출량은 ActiveRoast 완료 → plan 복귀 시 모달에서 입력
- **E5: 세션 노트**
  - 플랜 뷰 하단 textarea — 오늘의 메모 (날씨, 기온, 특이사항)
  - 날짜별 JSON에 `notes` 필드로 저장

## Data Model

```typescript
// src/shared/types/plan.ts
export interface PlanBatch {
  id: string;           // uuid-v4
  beanName: string;     // 자유 입력 or Beans 카탈로그에서 선택
  greenWeightG: number;
  profileId?: string;   // Profiles 카탈로그 ref (optional)
                        // 프로파일이 삭제된 경우: 로드 실패 시 undefined로 처리, 조용히 무시
  status: 'pending' | 'in-progress' | 'done' | 'skipped';
  // order 필드 없음 — 배치 순서는 batches 배열 인덱스로 결정.
  // 삭제 시 배열에서 제거하면 자동 재정렬. splice로 충분.
  // Populated after roast completes:
  roastedWeightG?: number;
  actualTimeSec?: number;
  roastId?: string;     // 저장된 로스트 ref (D1 완성 후)
}

export interface PlanBatchContext {
  batchId: string;
  beanName: string;
  greenWeightG: number;
  profileId?: string;
}

export interface DayPlan {
  version: 1;
  date: string;         // YYYY-MM-DD
  batches: PlanBatch[];
  notes: string;
  createdAt: string;    // ISO 8601
  updatedAt: string;
}
```

저장 방식: `tauri-plugin-store` (`@tauri-apps/plugin-store`) — 이미 설치됨.
Store: `LazyStore('plans.json')`, key = `YYYY-MM-DD`, value = `DayPlan` object.
**`tauri-plugin-fs` 추가 불필요.**

## State Machine: PlanBatch Status

```
         추가됨
           │
           ▼
        [pending]
           │
           │  "다음 로스트 시작" 클릭
           ▼
      [in-progress]
       │        │
       │        │  로스트 완료 (+ 배출량 입력)
       │        ▼
       │      [done]
       │
       │  "건너뛰기" 클릭
       ▼
     [skipped]

※ done/skipped → pending: 수동 '초기화' 버튼 (엣지케이스 대비)
```

## Context Passing: Plan → ActiveRoast

`ActiveRoast`는 현재 `App.tsx`에서 직접 props를 받음 (prop drilling 없음):
```tsx
<ActiveRoast isActive={view === 'roast'} onOpenRoastSettings={...} />
```
→ `planBatchContext` prop 추가만으로 연결 가능. React Context 불필요.

```
App.tsx (state)
  planBatchContext: PlanBatchContext | null  // 위에서 정의한 타입
  setPlanBatchContext: setter

Plan 뷰 → "다음 로스트 시작" 클릭
  1. planBatchContext = { batchId, beanName, greenWeightG, profileId }
  2. 해당 배치 status → 'in-progress' (저장)
  3. navigate to 'roast' view

ActiveRoast — 추가할 props:
  planBatchContext?: PlanBatchContext
  onPlanBatchComplete?: (result: { roastedWeightG: number; actualTimeSec: number }) => void

ActiveRoast 마운트/planBatchContext 변경 시:
  - roastNotes 초기값에 `beanName` pre-fill (현재 roastNotes는 이미 state로 관리)
  - greenWeightG → LiveReadings의 "투입량" 표시용 (현재 미표시, 추가 필요)
  - profileId pre-load: Profiles 카탈로그에서 조회, 없으면 무시

ActiveRoast 완료 (Drop → Summary → 닫기)
  1. onPlanBatchComplete({ roastedWeightG, actualTimeSec }) 호출
  2. App.tsx에서:
     - plan 파일 업데이트: status → 'done', 결과 저장
     - navigate to 'plan' view
     - planBatchContext 클리어

"다음 로스트 시작" 버튼 표시/비활성화 조건:
  - batches.length === 0: 버튼 숨김 (hidden, "+ 배치 추가"만 표시)
  - batches.length > 0 && pending === 0: 버튼 disabled + tooltip "모든 배치가 완료되었습니다"
  - in-progress 배치가 이미 있는 경우: 버튼 disabled + tooltip "진행 중인 배치가 있습니다"
  - pending 배치 있음: 버튼 활성화
```

## 배출량 입력 모달 (E3 — 로스트 완료 후)

ActiveRoast에서 로스팅 완료(Drop) 후 기존 RoastSummaryModal이 뜬다.
planBatchContext가 있는 경우, RoastSummaryModal에 배출량 입력 필드 추가:

```
필드: roastedWeightG (number, g 단위)
  - 유효성: 1 이상, greenWeightG 이하 (손실 없는 경우 없음)
  - 빈 칸 허용 (optional) — 입력 안 해도 모달 닫기 가능
  - 빈 칸 닫기 시: roastedWeightG = undefined (인라인 결과에서 '—' 표시)
취소/X로 닫기:
  - 배출량 없이 done 마킹 (roastedWeightG = undefined)
  - plan 복귀는 동일하게 실행
```

## 앱 크래시 시 in-progress 복구

앱 시작 시 (`useDayPlan` 훅 초기화 단계):
1. 오늘 날짜의 플랜을 로드
2. `in-progress` 상태 배치 탐색
3. 발견 시: 사용자에게 확인 다이얼로그 표시 (이중 로스팅 방지):
   ```
   "이전 세션에서 {beanName} 배치가 완료되지 않은 것 같습니다."
   [✅ 완료 처리] → status = 'done' (배출량 없이)
   [⏳ 다시 대기로] → status = 'pending'
   ```
   - 다음날 앱 오픈 시: 오늘 날짜 키 로드. 없으면 빈 DayPlan 생성.
     어제 날짜 키도 탐색 — in-progress 배치 있으면 동일 다이얼로그 (자정 크래시 대비).
   - 로그: console.warn으로 복구 시작 기록

**저장 실패 처리 (`store.set()` 에러 시):**
- `onPlanBatchComplete` → `store.set()` 실패 시:
  - 토스트 에러 표시: "계획 저장에 실패했습니다." + "재시도" 버튼
  - "재시도" 버튼 클릭 시: `store.set()` 재호출 (결과는 클로저로 버퍼링)
  - 재시도 성공 시: plan 뷰로 이동, planBatchContext 클리어
  - 사용자가 토스트 무시하고 수동으로 뷰 이동 시: 버퍼링된 결과 유실, 크래시 복구와 동일하게 pending으로 복구됨

## ETA 계산 예시

```typescript
// ETA는 pending 배치만 합산. in-progress 배치 제외 (이미 실행 중, 남은 시간 미추적 V1)
const pendingBatches = batches.filter(b => b.status === 'pending');
const DEFAULT_ROAST_SEC = 600; // 프로파일 없을 때 fallback
const totalSec = pendingBatches.reduce((acc, b) => {
  const profile = b.profileId ? profiles.find(p => p.id === b.profileId) : null;
  return acc + (profile?.estimatedTimeSec ?? DEFAULT_ROAST_SEC);
}, 0);
// → "남은 예상: 약 Xh Ymin" 포맷
```
