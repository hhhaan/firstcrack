# Existing source contracts for FSD-02 and FSD-03

These are source observations at implementation base 5c4649e86e9b9901fc7b68fc229ac31b7c5200cc, followed by implications of the selected design. They do not qualify a physical machine.

- `src/shared/lib/tsv.ts` exposes raw BT, acquisition timestamp, sensor clock, and per-sample processing metadata. Charge-relative `t` is distinct from the sidecar monotonic acquisition timestamp. The sensor clock parser requires a 32-digit hexadecimal process identifier and connection segment.
- `src/shared/lib/tsv-writer.ts` already archives those fields and repeats processing metadata when it changes. Preserve this archive rather than creating a second temperature recorder. The control algorithm's filter version is separate from the archive's display-processing settings.
- `src/entities/roast-profile/queries.ts` returns `source` as session, synthetic, or none. Its synthetic fallback has neither raw provenance nor acquisition timing. FSD must require the real source and reject the fallback.
- The profile source join in `src/entities/roast-profile/api.ts` currently omits machine identity. Existing `roast_sessions` schema already has machine_id, machine_roaster_key, machine_protocol, and machine_name. FSD-03 can extend the existing join and entity shape without a database migration. Do not infer source machine identity from the current selection.
- `src/features/active-roast/model/useRoastActions.ts` obtains the new roast session ID, computes the existing manual/backdated origin, then calls bodyless `sidecar.startRoast()`. FSD-02 must transmit the ID and an accepted source anchor, return authoritative Charge timing, and preserve legacy bodyless start as ineligible for curve control.
- Live TP has a fallback flag, but stored TP events encode the fallback in a human-readable note. An editable note is insufficient control provenance. The sidecar must independently qualify reference and live raw evidence using the selected virtual rule. The existing UI detector has different thresholds; do not silently treat UI eligibility as sidecar qualification.
- `src/features/active-roast/lib/serialize-roast-events.ts` already serializes `applied_control` and uses it for History control changes. History log rows intentionally omit Control events. Extend these established paths for sequenced receipts and uncertainty metadata; do not fabricate complete PID history from sampled heater_set values.
- The virtual thermal adapter responds to actual heater commands, but its default model begins at ambient and has no Charge cooling phase. A test requiring observed TP must establish a real cooling-and-recovery trace under manual virtual controls or use an explicit thermal fixture with declared initial conditions. Scripted demo BT does not prove closed-loop heat response.

The selected design already specifies the virtual control filter, TP criterion, source history, bounds, lease, and receipt journal. Keep those separate from physical qualification and from the UI's existing display smoothing.
