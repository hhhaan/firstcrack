# Deep Review — 정교한 코드 분석 보고서 생성

`febeldocs-pre-deployment-validation.md`와 `comm-layer-hardening.md`와 동일한 수준의 코드 리뷰/분석 보고서를 생성하는 방법론. **파일 인벤토리 → 사실 검증 → 심각도 분류 → 증거 기반 문제 기술 → 수정 방안 → 검증 체크리스트 → 비이슈 기록**의 전 과정을 안내한다.

**Arguments:** 분석할 코드 영역/컴포넌트/문제 설명을 받는다. 예: "사이드카 프로세스 생명주기 분석", "통신 레이어 강화 설계 검토", "모달 시스템 보안 감사".

**출력물:** `plans/<feature>-<focus>.md` 형식으로 저장한다.

---

## 0. 사전 조건 확인

시작하기 전에:
- 분석 범위가 분명한가? 모호하면 `ask`로 질문을 던져 범위를 구체화한다.
- 출력 디렉토리 `plans/`가 존재하는가? 없으면 생성한다.

## 1. 파일 인벤토리 (File Inventory)

분석 대상 코드베이스의 관련 파일을 **전수 조사**하고 각각의 **역할**을 표로 정리한다.

**수행:**
- `explore` 또는 `glob`으로 관련 파일 검색
- 각 파일을 `read_file`로 확인하고 역할을 파악
- 3열 표로 정리 (File, Role, Key lines/notes)

```
| 파일 | 역할 | 주요 내용 |
|---|---|---|
| src-tauri/src/lib.rs | 사이드카 스폰/kill/재시작 | 187-252 restart loop |
| ... | ... | ... |
```

**규칙:**
- 역할은 **동사+명사** (예: "사이드카 생명주기 관리", "설정 읽기/쓰기")
- 주요 내용은 **라인 범위 + 간략 설명**
- 추측하지 말고 실제로 파일을 읽은 후에만 작성

## 2. 사전 검증된 사실 (Pre-verified Facts)

"사실인지 확인된 것"과 "추측"을 분리한다. 이 섹션은 코드를 **직접 확인**한 결과만 기록한다.

**수행:**
- 각 주장에 대해 실제 코드(또는 문서)를 **읽고** 확인한다
- `plugin-shell 2.3.5 소스 확인` 처럼 확인 근거를 명시한다
- 파일:라인을 반드시 함께 기록한다

```
사전 검증된 사실 (추측 아님):

- tauri-plugin-shell 2.3.5 소스(`src/process/mod.rs:173`)에서 CREATE_NO_WINDOW 적용 확인.
- `kill_zombie_sidecar()` Windows 경로(`lib.rs:63,88,95`) — creation_flags 처리 완료.
```

**규칙:**
- 절대 추측을 적지 않는다 — "아마도", "추정"은 여기가 아니라 아래 이슈 섹션에 적는다
- 이 목록이 길수록 분석의 신뢰도가 높아진다

## 3. 이슈 발굴 및 분류 (Issue Discovery & Classification)

이슈를 발견하고 다음 체계로 분류한다.

### 분류 체계

| 레벨 | 코드 | 기준 | 예시 |
|---|---|---|---|
| 치명적 | **Critical** | 사용자 데이터 손실, 기능 완전 차단, 보안 위반 | C1, C2, C3 |
| 주의 | **Warning** | 특정 조건에서 기능 이상, 부차적 경로 차단 | W4, W5 |
| 정보 | **Info** | 현재는 문제없지만 추적 필요, 회귀 방지 | M3, X3 |

### 각 이슈의 구조

모든 이슈는 다음 구조를 **반드시** 따른다:

```
### C1. 제목 (간결하고 서술적)

**플랫폼: Windows + macOS 공통 · 심각도: 최상 · 위치: lib.rs:260-267**

(문제 설명 — 2-4문장. 무슨 코드가 어떻게 동작하고, 무엇이 잘못되었는지)

```코드
// 문제가 되는 코드 조각
```

**결과:**
- 결과 1 (사용자에게 어떤 영향인가)
- 결과 2
- 결과 3

**재현:**
1. 단계 1
2. 단계 2
3. 단계 3

**수정 방안 (권장 순):**
- **(a) 제안 1** — 설명, 장단점, 코드 예시
- **(b) 제안 2** — 설명, 장단점
- (c) 제안 3 (부적합 사유 포함)
```

**규칙:**
- 핵심 코드 조각을 반드시 포함 (파일:라인 표기)
- 결과(consequences)는 사용자/배포/운영 관점에서 작성
- 재현(reproduction)은 누가 따라할 수 있게 구체적으로
- 수정 방안은 최소 1개, 최대 3-4개. 권장 순서대로 (a)(b)(c) 표시
- 각 제안의 **트레이드오프**를 명시 (더 견고하지만 복잡하다, 단순하지만 모든 경로를 커버하지 못한다 등)
- 부적합한 제안(d)은 명시적으로 배제 사유와 함께 기록

## 4. 플랫폼/컨텍스트별 우려 사항 (Platform/Context Concerns)

이슈를 플랫폼(Windows/macOS/Linux), 환경(dev/prod), 레이어별로 분류해 서술한다.

### 템플릿

```
### 4-1. Windows

**W1. 제목 — 설명** (`file:line`)
본문...

**W2. 제목 — 설명** (`file:line`)
본문...

### 4-2. macOS

**M1. 제목 — 설명** (`file:line`)
본문...
```

**규칙:**
- 각 항목은 `{접두어}{번호}. 제목` 형식 (W1, W2, ..., M1, M2, ..., X1, X2, ...)
- 접두어: W(Windows), M(macOS), L(Linux), X(공통), D(Dev 경험), S(보안)
- 각 항목마다 **파일:라인**을 반드시 표기
- 필수가 아닌 경우 "인지용", "선제 대응", "후속 작업" 등 성격 표시

## 5. 권장 수정 사항 (Recommended Fixes)

표로 요약한다:

```
| # | 작업 | 대상 파일 | 난이도 | 효과 |
|---|---|---|---|---|
| 1 | parent-PID 워치독 추가 | main.py, lib.rs | 중 | C1 해소 — 고아 차단 |
| 2 | ... | ... | ... | ... |
```

**규칙:**
- 우선순위 순으로 정렬
- 묶어서 처리해야 하면 "1-3번은 한 PR로 묶음 권장" 명시
- 난이도: 하/중/상
- 효과: 해소되는 이슈 ID 표기

## 6. 검증 체크리스트 (Verification Checklist)

수정 후 반드시 확인해야 할 항목을 체크리스트로 작성한다.

```
### 공통
- [ ] 항목 1 (연관 이슈)
- [ ] 항목 2

### Windows 전용
- [ ] 항목 3

### macOS 전용
- [ ] 항목 4
```

**규칙:**
- 각 항목은 **실행 가능한 동사로 시작** ("확인한다" 말고 "프로덕션 빌드 설치 → 실행 → 정상 종료 → 프로세스 목록 확인")
- 괄호로 연관 이슈 ID 표시
- 체크리스트는 수동 테스트용 — 자동화 가능하면 따로 표시

## 7. 명시적 비이슈 (Explicitly NOT Issues)

오판을 방지하기 위해 **"문제 아님"으로 확인한 항목**을 기록한다.

```
- **항목** — 확인 근거 (파일:라인)
```

**규칙:**
- 이 섹션이 없다면 검토자가 "이것도 체크했나?"라고 다시 묻게 됨 → 비용 발생
- "문제 아님"으로 판정한 **모든** 후보를 기록
- 각각에 **왜 문제가 아닌지**와 **확인 방법**을 명시
- 미리 봤으면 좋았을 것들: FAQ 성격, 오해하기 쉬운 포인트

## 전체 규칙

1. **추측 금지** — 모든 주장은 코드/문서 읽기 기반. "아마도", "~일 것이다"는 사전 검증된 사실에 넣지 않는다.
2. **파일:라인 필수** — 모든 코드 참조는 파일 경로 + 라인 번호를 함께 표기한다.
3. **체인 인과관계 명시** — C1이 C2를 유발하고 C3와 결합된다면 그 관계를 반드시 설명한다.
4. **수정 방안의 트레이드오프** — 각 제안의 장단점을 함께 쓴다. "왜 (a)가 (b)보다 나은가"에 대한 근거.
5. **출력물 저장** — 결과는 `plans/<feature>-<focus>.md`에 저장한다.
